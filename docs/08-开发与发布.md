# 开发、测试与发布

## 开发环境

需要Python 3.11或更新的兼容版本、Git；Windows安装包构建另外需要PyInstaller和Inno Setup 6。建议在D盘创建隔离环境，安装requirements-build.txt，不让最终用户安装Python。

复制config中的两份模板到根目录后运行src/freight_app.py --mode start。真实配置、日志和数据库均不应提交。公开模板没有群，测试使用合成群fixture。

## 验证

运行scripts/run_tests.ps1执行回归；网页/安装器测试使用隔离端口和数据目录，不连接实际业务QQ。发布前要测试真正的安装包，而不是只测试源码。

至少包括：空配置首次启动、带空格和中文路径、无Python环境、升级保留配置/数据库/暂停状态、群过滤、重复消息、未来日期、持久队列重启、断网重连、坏Token/坏配置拒绝、端口冲突、文件占用、查询删除、日图快照和年度归档。

## 构建

使用scripts/build_release.ps1 -Version 1.4.2 -Python python。脚本仅清理本仓库下的build和dist-release，先运行回归，再校验锁定的官方NapCat组件并构建、做打包冒烟测试。不要在含个人输出的目录运行清理命令。

安装器、便携包、SHA256SUMS.txt输出到dist-release。build-info.json记录来源提交、源码树和运行依赖；release-manifest.json记录便携内容哈希。

公开包不能包含真实聊天、群号、数据库、QQ.exe、登录状态和凭据。NapCat官方组件必须保留许可与来源；其非商业限制需显著说明，不改写上游代码。

## 发布闭环

1. 使用发布分支和Conventional Commits；检查全部变更、隐私和CI。
2. 冻结源码提交，构建最终资产。若修复导致资产变化，重新构建并重跑发布前验收。
3. PR、标签与Release指向可追踪源码，不能覆盖旧标签。附上校验和、构建信息与实际测试报告。
4. 发布后从GitHub重新下载资产，检查SHA-256与发布前文件完全相同，再在新目录安装和重跑同一业务链路与异常场景。
5. 新版验证通过后才标记Latest；旧版保留回退。失败报告不能删改冒充通过，安装与运行环境未覆盖的部分明确列出。

首次扫码登录与账号风控必须本人处理；不能声称已在每个Windows版本、每种杀毒软件、真实磁盘耗尽或全年不间断生产环境验证。
